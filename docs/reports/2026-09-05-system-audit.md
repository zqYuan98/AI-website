# notvitamin.com 系统级审查

审查日期：2026-09-05（Asia/Shanghai）  
审查对象：[notvitamin.com 正式站](https://www.notvitamin.com/)  
代码基线：`c7f9ed4903299182290446eb24fc4748429d3525`  
性质：只读审查与研究；未修改应用代码、依赖、线上配置或部署。

## 1. 核心结论

**值得保留现有技术底座和视觉语言。当前短板不是框架不够先进，而是内容证据、访客任务路径和持续发布的质量保障还没有形成闭环。**

这是一个适合采用「静态内容为主、局部交互、单一代码库」的网站。已经具备：一致的蓝白视觉、明确的 AI 产品方向、作品/博客/工具/Lab 的模块边界、本地图标、真正可操作的 Lab，以及与独立商店的清晰分离。没有证据支持现在换框架、拆微服务或引入数据库。

但“好看的个人展示站”和“可持续经营的个人品牌系统”之间还有一段距离：

- 三篇博客正文只有约 75～154 个非空白字符，却标注 6～8 分钟阅读；主案例仍是简短概述。
- “写一封自我介绍”没有对应邮件入口或表单，联系区只提供 GitHub 和返回作品。
- 工具页加载并不慢，但手机用户到达搜索和列表仍需明显滚动；筛选状态不能保存到网址。
- 业务回归仍依赖人工检查；没有提交锁文件，依赖树无法从当前仓库完整复现。
- 实验室性能成绩良好，但没有拿到真实用户性能、目标地区可用性和转化数据。

建议把“最优”定义为四件可验收的事：**访客更快完成任务、内容更可信、修改更安全、长期维护更省力。** Lighthouse 分数只是其中一个指标。

### 综合判断

| 维度 | 当前判断 | 最值得投入的方向 |
|---|---|---|
| 品牌与视觉 | 基本一致，可保留 | 保留蓝白、卡通形象和轨道动效；按页面任务调整信息密度 |
| 响应式布局 | 前轮主要溢出问题已修复 | 补键盘、横屏、长列表和任务可达性，不再只看是否横向溢出 |
| 加载性能 | 本次代表页实验室成绩良好 | 实际用户测量、减少无效媒体请求、守住回归预算 |

## 3. 真实性能：已经较好，但要分清测到了什么

### 3.1 代表页实验室结果

2026-09-05 13:04～13:08 UTC，Lighthouse 13.4.1，Windows 上 Headless Chrome 151。移动测试采用默认模拟参数：412×823、DPR 1.75、RTT 150ms、吞吐 1638.4Kbps、CPU 4 倍减速；桌面为 1350×940、DPR 1、RTT 40ms、10Mbps、CPU 不减速。**每个场景一次，不是多次中位数，不是真机测速。**

| 页面 / 模式 | 性能分 | LCP | TBT | CLS | Speed Index | 本次加载总传输量 |
|---|---:|---:|---:|---:|---:|---:|
| 首页 / 移动 | 95 | 2.179s | 29ms | 0.000052 | 5.075s | 827KiB |
| 工具 / 移动 | 96 | 2.294s | 14ms | 0 | 3.109s | 369KiB |
| Lab 清单 / 移动 | 99 | 1.687s | 9ms | 0 | 2.070s | 300KiB |
| 首页 / 桌面 | 99 | 0.691s | 0ms | 0.000016 | 1.193s | 892KiB |

总传输量为 Lighthouse 本次加载记录，包含该次加载的媒体等资源，不是 JS 包大小，也不代表滚动完整页之后的累计字节。四份报告没有 runtimeError 或 runWarnings；部分 CLI 在完成报告后清理 Windows 临时 Chrome 目录时报 EPERM，不影响已生成的测量内容。

**解读：目前没有“框架拖垮网站”或严重首屏布局跳动的证据。** 不应为了从 95 变为 100，就撤掉用户明确希望保留的品牌动效或重写整个站点。

首页移动端 Speed Index 约 5.1s，是本次更明显的视觉完成时间短板。持续动效可能影响这个测量，但没有做禁用视频/动效的对照实验，不能把原因直接归到视频上。若继续专项优化，应先做保持静图一致的受控对照，再判断带宽竞争或动效本身的影响。

真实用户目标应看移动/桌面分别统计的 P75：LCP ≤2.5s、INP ≤200ms、CLS ≤0.1。这里的 TBT 是实验室指标，不能当作 INP；也不能凭一次测试宣布真实用户 Core Web Vitals 已达标。[Google Web Vitals 定义与测量边界](https://web.dev/articles/vitals)

### 3.2 首页动效：保留，但减少无效传输

当前首页实际使用 MP4，不是把原始大 GIF 当主播放资源。移动测试中视频传输约 438KB，约占该次总加载量的 52%；LCP 元素却是优化后的约 17.9KB WebP Hero 图，相关加载发现检查通过。**视频有带宽成本，但没有证据证明它已造成 LCP 不达标。** 磁盘上 2～4MiB 的原始 PNG，也不能直接当浏览器下载量。

一个更明确的问题：在开启 `prefers-reduced-motion` 后再加载的独立测试中，视频 `display:none`、`paused:true`、播放时间为 0，仍下载了完整 437,393B 视频内容。原因是 HTML 仍无条件提供 video source，仅 CSS 隐藏。

证据：[首页 video](../../src/app/page.tsx#L72)、[减弱动效 CSS](../../src/app/globals.css#L610)。减少动态效果请求记录来自审查时的临时浏览器取证，未纳入版本库。

建议：保留默认用户的大动效和静态封面；减弱动效模式不要装载视频 source，增加可见的暂停/继续入口。再根据实际情况考虑离屏暂停、后台暂停及省流策略。不要把全部 Hero 变成延迟加载，避免反而影响静态 LCP 图。持续自动播放内容也应检查是否需要暂停机制。[W3C Pause, Stop, Hide](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)

### 3.3 工具页：展示分页不等于数据分页，但现在不需要后端

手机初始 18 张、桌面 36 张工具卡已生效；浏览器仍接收全部 268 条公开数据。[ToolsExplorer 数据边界](../../src/app/tools/page.tsx#L145)

当前数据体积：

- 268 条工具的公开 JSON：原始 103,645B；单独压缩约 gzip 13,155B / Brotli 9,891B。
- 工具页完整 HTML：解码约 442,450B，另一次浏览器测量的 Brotli 内容约 51,552B。
- HTML 中同时存在 RSC 序列化数据、结构化数据和无 JS 入口。它们有不同用途，不能简单认定都是应该删除的重复内容。

这些大小的测量对象不同，不能相加，也不能把原始 JSON 或解码 HTML 当线上总传输量。现在的工具页移动性能是 96，**不值得仅为 268 条收藏引入数据库/API 请求链。**

低成本优化顺序：

1. 在数据准备阶段一次生成 hostname 和各搜索字段的归一化文本，避免每次输入对每条工具重复创建 URL、处理大小写；保持当前“任一字段包含关键词”的匹配规则，不直接拼接字段后引入跨字段短语匹配。
2. 公开数据只保留客户端需要的字段；目前 `order`、`updatedAt` 未在工具交互组件使用。
3. 保留普通收藏与作者实践背书的区别，保留可阅读的静态内容入口。
4. 真正出现数据或输入性能压力后，再把静态搜索索引与详情分片分开；必要时才用 Worker 或服务端搜索。

桌面 Node 的只读微基准也提示应先消除重复准备工作：268 条当前扫描 P95 约 3.95ms，循环复制到 5000 条约 35.92ms；预拼接搜索文本的对照分别约 0.04ms、0.11ms。对照未验证与原有逐字段匹配的完整行为等价性，不能作为可直接上线的收益承诺。这里不包含 React 渲染、手机 CPU 和网络，重复样本也不能用于推算真实压缩率或 INP。

### 3.4 资源与缓存：没有必要重新搭一层缓存系统

| 移动页面 | JS 传输 | CSS 传输 | 图片传输 | 视频传输 |
|---|---:|---:|---:|---:|
| 首页 | 156,870B | 19,913B | 138,051B | 437,855B |
| 工具 | 162,654B | 19,908B | 77,890B | 0 |
| Lab | 166,429B | 24,303B | 33,486B | 0 |

三份移动报告中的第三方资源请求均为 0。线上 HEAD 代表页有 `X-Nextjs-Prerender:1` 与 `X-Vercel-Cache:HIT`；哈希 JS 使用一年 immutable 缓存。HTML/视频的 `max-age=0,must-revalidate` 不能解读为 CDN 没有缓存；本次没有做重复访问缓存对照。

工具图标使用本地资源且未启用在线图片转换，多张 128px PNG 显示约 28px。Lighthouse 估计其中 7 张可节省约 49KiB，但预估 LCP 改善为 0ms。因此可在维护媒体时离线生成合适尺寸/格式的小图，属于低优先级带宽优化，不是紧急首屏故障。[ToolIcon](../../src/components/tools/tool-icon.tsx#L21)

### 3.5 国内访问：这是可能影响更大的基础条件

当前暂按“中文用户为主、兼顾海外”理解，尚未得到用户地域确认。本次测试不是大陆多运营商现场测量。

Vercel 官方说明其没有中国大陆 CDN 节点或服务器，不能保证大陆地区的可用性与性能；独立域名也不等于解决所有跨境链路问题。[Vercel 大陆访问说明](https://vercel.com/kb/guide/accessing-vercel-hosted-sites-from-mainland-china)

建议先取得真实目标用户网络数据，区分 DNS/连接/首字节、静态资源和客户端执行时间。若主要问题来自跨境访问，再比较可靠路由或静态镜像方案，并单独评估维护和合规成本；现在不要盲目再套一层代理、购买 CDN，或认为修改函数区域就一定能解决静态站访问问题。

## 4. 设计审查：保持同一种品牌，不必让每页都像宣传页

### 4.1 页面角色与调整方向

| 页面 | 应帮助访客完成什么 | 当前判断 | 建议 |
|---|---|---|---|
| 首页 | 快速理解方向，看到最强证据 | 主张、配色与动效统一；三张作品权重接近 | 变为一个突出主案例、两个辅助作品；工具/Lab 是下一步，不抢主线 |
| 关于 | 判断经历与合作适配度 | 卡通形象和文字方向合适 | 保留“维他命”署名，不出现真名；联系区给明确可执行入口 |
| 作品列表 | 快速筛选项目与成熟度 | 卡片统一，但成熟度信息不突出 | 区分实践、MVP 验证、已交付；状态必须由真实证据支撑 |
| 作品详情 | 理解问题、判断、证据和责任边界 | 当前更像摘要页 | 主案例补问题背景、个人角色、关键取舍、证据、限制和下一步 |
| 博客 | 获得一个完整判断或框架 | 列表比正文更完整 | 短内容标为短札/观点；长文有完整论证，不靠虚高阅读时长 |
| 工具 | 找到并打开工具，方便以后再来 | 功能基本好用；手机操作入口仍靠后 | 搜索和分类前置；收藏量可扩张，精选背书保持克制 |
| Lab | 打开即用，并带走结果 | 本地保存、导出和边界提示是亮点 | 保留独立工具形态；将“开始使用”的路径做短 |
| 商店外链 | 在有信任的前提下查看供给 | 独立 notvitamin.xyz 的边界合理 | 清楚说明跳转独立站；不在主站重复做订单和支付系统 |

### 4.2 工具页的实际任务距离

线上 390×844 视口，搜索框在文档 Y≈1040px，第一张工具卡在 Y≈1281px，初始页面总高度约 6636px。即使页面加载很快，访客仍要先通过较长介绍才能执行搜索。

建议手机工具页采用「简短标题 / 总数 → 搜索 → 分类 → 列表」，把长主张与大图缩短、折叠或后置。保留主页的完整品牌表达。**视觉一致指共享字体、色彩、边框和交互状态，不等于每页必须占用同样大的 Hero。**

用户明确希望持续收藏工具，所以不建议删掉全量集合或强制每条都写长评。更合适的两层：

- **全部收藏**：网址、名称、分类即可加入，描述和图标可自动辅助；没有真实体验就不写“我在用”。
- **维他命精选**：少量带实际场景、推荐理由和边界的条目，由真实经验升级产生。

开发分类可以继续存在；在分类之上提供少量任务入口，如“做研究”“做原型”“部署上线”。这是对原分类的补充，不是另造一套需要重复维护的目录。收藏数是资产规模，精选判断才是个人品牌差异。

### 4.3 已确认的键盘交互问题

在 844×390 横屏打开手机导航，焦点到最后一个商店链接后按 Tab，焦点进入首页“查看我的作品”按钮，但菜单仍展开且页面滚动锁定。该按钮被菜单遮住；中心点命中的是菜单中的“博客”。

当前 Escape 关闭并恢复焦点的修复有效，不是本条问题。缺口是焦点离开菜单时的行为。[Header 状态管理](../../src/components/header.tsx#L18)

优先考虑保持普通导航展开模式，焦点离开展开区域时关闭；若以后改为真正模态覆盖层，再按 dialog 模式管理焦点及背景可交互性。不要随意给普通导航加 `role="menu"`。本次是可复现的可用性问题，不是完整 WCAG 合规判定。[W3C Disclosure Navigation 示例](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)

### 4.4 统一样式的正确范围

代码中有可以收敛的覆盖链，例如 Tools 的 `.toolCard` 先声明 27rem 最小高度，又在后面覆盖为 12rem；`toolGrid` 间距也重复覆盖。这比“CSS 文件有多少行”更影响维护判断。[原规则](../../src/components/tools/tools.module.css#L378)、[后续覆盖](../../src/components/tools/tools.module.css#L890)

建议统一语义色、容器宽度、间距尺度、圆角、边框、按钮状态；工具卡、作品卡和文章行保留各自需要的信息密度。固定浅色模式下，`next-themes` 与未使用暗色规则可作为低优先级整理项；不要为了补暗色功能扩大本轮任务。客户端 Provider 包住服务端 children 并不意味着整站变成客户端渲染。

## 5. 内容与转化：当前最重要的系统缺口

### 5.1 阅读时长与正文不匹配

计数口径：读取 Markdown 正文，排除 frontmatter 和空白；包含标点及 Markdown 标记，因此是非空白字符数，不是中文词数。

| 博客 | 当前标注 | 正文非空白字符 |
|---|---|---:|
| 企业 AI 别一上来就造 Agent | 6 分钟 | 75 |
| 从让模型看见，到让 AI 真正工作 | 7 分钟 | 92 |
| 我为什么把自己定位成 AI 时代的产品经理 | 8 分钟 | 154 |

证据：[Agent 文章](../../content/blog/dont-start-with-agent.md#L5)、[主张文章](../../content/blog/from-seeing-to-working.md#L5)、[定位文章](../../content/blog/why-ai-era-pm.md#L5)。

建议立即让阅读时长与正文一致，或暂时不显示估算。保留短观点完全合理；问题不在短，而在承诺与实际阅读体验不一致。需要长文时，用真实案例、反例、判断步骤和适用边界完善，不按搜索字数指标灌水。

### 5.2 主案例缺少独立支撑判断的证据

“数智值班员”正文约 195 个非空白字符，当前如实说明仍在 MVP 验证阶段。这不应改写成已经产生显著业务成果。

主案例应至少让外部读者独立理解：

1. 原工作方式的问题是什么，谁受到影响。
2. 你具体负责什么，团队或其他角色负责什么。
3. 为什么选择现在的方案，放弃了哪些方案。
4. 哪些是模型候选、哪些由规则或人确认；失败如何接管。
5. 已有什么证据：脱敏流程、原型、评审记录、测试样本、验收标准或真实结果。
6. 当前没有证实什么，以及下一步怎样验证。

没有数据就提供真实过程证据和验证计划，不伪造增长率、准确率或客户评价。当前概念型封面与站点视觉匹配，但不能充当产品实证；可保留封面，并在正文使用有权限发布的脱敏材料，必要时明确“概念示意”。[主案例源文件](../../content/work/digital-duty-officer.md)

### 5.3 联系入口承诺没有兑现

页脚“写一封自我介绍”链接到 `/about#contact`。该区域只有 GitHub 与“先看作品”，没有邮件链接或联系表单。并非完全无法接触作者，但对非开发者合作方很不直接。

建议在用户提供实际可公开联系方式后，增加一个清楚的联系动作；在此之前，可以将入口准确表述为“联系与合作”。不要替用户编造邮箱，也无需先搭建客户管理系统。[页脚 CTA](../../src/components/footer.tsx#L71)、[联系区](../../src/app/about/page.tsx#L171)

### 5.4 模块需要互相解释，而不是只由导航栏连接

目前三篇博客正文没有站内 Markdown 链接；博客详情模板在正文后结束。作品详情有其他作品，但没有对应的方法文章、工具或联系路径。Lab 已经有相关作品、博客和工具入口，可以作为可复用的模式。

建议在内容中维护少量 `relatedWork / relatedPosts / relatedTools / relatedLabs` 标识，由页面渲染真正相关的下一步，而不是每页机械放同一组广告卡：

`案例提供证据 → 博客解释判断 → Lab 提供方法 → 工具支持执行 → 合适时联系或进入商店`

这条路径能同时服务读者理解、回访和内容发现。无需知识图谱数据库；经过存在性校验的关联 ID 就足够。

### 5.5 SEO / GEO 的合理位置

遵守此前要求：不新增一个 SEO 基建模块，也不把此次优化变成关键词工程。真正有价值的是一篇文章能够独立回答问题，一张案例页能证明经历，一个 Lab 能实际使用。

Google 关于有用内容的指南强调作者、方法和内容价值；这不要求公开真名，可以继续使用“维他命”，配合一致的作者介绍和可验证的经历。[Google 有用内容指南](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

Google 也说明 AI Overviews / AI Mode 没有额外的专用 AI 文件或特殊 schema 门槛。此结论仅针对 Google 的相应功能，不能推广成所有模型平台的引用保证。[Google AI 功能说明](https://developers.google.com/search/docs/appearance/ai-features)

有一个应随内容完善处理的分发问题：线上博客和作品的普通 title/description 独立，但 Open Graph 标题、说明和 URL 仍继承首页，且未提供 og:image；工具与 Lab 已有自己的分享信息。分享具体文章时不应看起来仍是首页。可在共同内容模板里补对应分享信息，而不是单独再造一个系统。[根布局 metadata](../../src/app/layout.tsx#L16)、[博客 metadata](../../src/app/blog/%5Bslug%5D/page.tsx#L17)

## 6. 最小而优雅的目标架构

### 6.1 保持单一代码库、静态优先、交互局部化

```text
作者维护（本地表单 / Markdown / JSON）
                  │
        内容校验 + 媒体/链接校验
                  │
         Git 版本 + 自动质量门槛
                  │
        服务端内容读取 / 轻量索引
           ┌──────┼────────┐
           │      │        │
       静态内容页 工具公开数据 Lab 定义/路由登记
           │      │        │
           │   URL筛选状态  版本化本地进度
           └──────┼────────┘
                  │
          CDN 页面 / 本地静态资源
                  │
        必要的性能、错误、任务事件

独立边界：notvitamin.xyz 负责商店、订单与交付
```

RSC 即服务端组件：内容处理留在服务端/构建阶段，客户端只承担搜索、筛选、菜单和清单等交互。当前已经接近这条路线，改进重点是边界明确、重复工作减少和约定可检查，而不是文件夹数量更多。[Next 服务端与客户端组件](https://nextjs.org/docs/app/getting-started/server-and-client-components)

### 6.2 内容合同统一，避免静默错误

工具数据验证较严格，但 Blog/Work 对缺字段使用 fallback；错误日期字符串会原样通过。Lab 的日期仅匹配格式，内存调用现有函数确认 `2026-02-31` 和负的小数 order 能通过。**现有内容没有检出这些错误，问题是未来编辑缺少保护。**

建议共用验证原语，但保留各模块自己的 schema：有效日期、必填文本、合法 slug、非负整数顺序、已存在的封面和站内关联等。无效内容应在检查/构建时给清楚错误，而不是悄悄上线。阅读时长等可推导字段尽量自动计算。

证据：[Blog/Work 容错](../../src/lib/content.ts#L65)、[Lab 日期](../../src/lib/labs.ts#L93)、[工具验证](../../src/lib/curation.ts#L145)。

### 6.3 工具状态进入 URL，但不把页面改成动态后端查询

实际搜索 NotebookLM 后得到 1 张卡，但 URL 仍为 `/tools`；重新打开又回到默认 18 张。这阻碍收藏具体分类、分享筛选结果和浏览器历史恢复。

建议查询、分类、子分类、精选和工具/资源视图进入 URL；侧栏展开、加载数量保留在局部状态。输入可替换当前历史，明确切换分类可建立新历史。处理未知参数、前进后退和清除逻辑。Next 支持原生 History API 与路由状态同步，无需因此给整页增加服务端请求。[筛选状态源码](../../src/components/tools/tools-explorer.tsx#L259)、[Next History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api)

### 6.4 Lab 是值得保留的交互样板

当前清单已有版本化存储键、有效 ID 白名单、损坏 JSON 保护、存储不可用时降级、跨标签同步、复制失败后的手动后备和下载能力。18 项清单没有必要换成全局状态管理或云数据库。[清单实现](../../src/components/lab/acceptance-checklist.tsx#L6)

未来修改检查项含义时，要明确旧勾选状态是否仍有效；更换语义应升级版本或迁移。只有用户确实需要跨设备账户同步，再考虑认证和远端持久化。

新增第二个实验时，增加轻量 registry 统一实验 slug、内容和实际入口。当前只有一个手写实验路由，而目录自动读取所有 Lab Markdown，sitemap 又单独写地址；以后只加 Markdown 会出现目录中有项目但没有可用页面的风险。当前没有这个坏链接，不需要提前建设“万能实验引擎”。[Lab 目录读取](../../src/lib/labs.ts#L142)、[sitemap](../../src/app/sitemap.ts#L13)

### 6.5 扩张要由成本与测量触发

| 条件 | 优先做什么 | 还不必做什么 |
|---|---|---|
| 当前 268 个工具，单人维护 | 内容校验、URL 状态、预计算搜索文本 | 数据库、搜索集群、登录系统 |
| 上千条，低端手机出现输入/内存压力 | 实测后拆静态搜索索引与详情，按需加载 | 仅凭条数迁移后端 |
| 内容增长导致构建明显变慢 | bySlug 直接读取、构建索引、去除重复解析 | 先上 Redis 或全站动态渲染 |
| 多作者、并发编辑、权限或审核成为日常需求 | 再评估 CMS/数据库及发布工作流 | 当前为未来假设维护完整后台 |
| Lab 需要跨设备同步或处理私密数据 | 独立认证/存储边界与相应安全审查 | 把全部公开内容也变成有状态应用 |

现有 loader 的单条查询会先遍历整个内容目录，生成大量详情页时可能产生约 O(N²) 文件解析；目前只有 3 篇博客和 3 个作品，主要是未来构建效率问题，不能描述成每次线上静态请求都在读盘。[内容读取](../../src/lib/content.ts#L163)

## 7. 发布、安全与运维

### 7.1 最先补齐发布的可复现性

仓库根目录和 Git 索引没有锁文件；虽然 Next/React 的直接版本固定，其他依赖存在范围版本，传递依赖也没有完整锁定。`packageManager` 声明 Bun 1.4.0，但仅有该声明不能复现完整安装树。

建议选定并固定一套包管理工具，生成并提交对应锁文件，在 CI 使用 frozen 安装；不要混用多种锁文件让各环境自行选择。Bun 的官方说明要求提交 `bun.lock` 才能使用 `bun ci` / frozen 安装实现此类约束。[Bun 安装与 CI](https://bun.sh/docs/pm/cli/install)

这不是“当前网站发布失败”，也不是“发现依赖漏洞”，而是同一份代码未来重新构建时可能得到不同依赖的风险。

### 7.2 自动质量门槛缺失

仓库没有 `.github/workflows`；脚本只有 dev/build/start/lint，build 为 `next build`。`scripts/check-tools.mjs` 已经存在，但未自动接入脚本链。本次提交公开 GitHub status 是 4 个 Vercel 部署成功，check-runs 为 0。

最小发布链应是：冻结依赖安装 → 内容验证 → lint/typecheck → 构建 → 生产模式关键路径冒烟 → 部署后确认域名和版本。检查必须真正阻止错误版本进入正式环境；仅增加一个不约束部署的绿色工作流还不够。

证据：[脚本配置](../../package.json#L5)、[提交部署状态](https://api.github.com/repos/zqYuan98/AI-website/commits/c7f9ed4903299182290446eb24fc4748429d3525/status)、[检查记录](https://api.github.com/repos/zqYuan98/AI-website/commits/c7f9ed4903299182290446eb24fc4748429d3525/check-runs)。项目级构建命令覆盖和分支保护本次不可见，需要后续有权限时核对。

同一个 Git 提交触发了 ai-website、notvitamin、notvitamin-site、vitamin-site 四个 Vercel 项目。正式域名对应 ai-website。建议先列清用途、域名、环境和回滚路径，再决定哪些有保留必要；不应直接删除其他项目，也不能据此计算实际费用浪费。

### 7.3 已有安全边界是有效的

- 生产环境维护页面和 API 独立关闭；API 在解析请求、联网和写入前拒绝非 development。[API guard](../../src/app/api/local-tools/route.ts#L65)
- 本机维护校验 Host、Origin/端口和跨站标记；默认开发服务绑定 127.0.0.1。
- 维护入口限制 JSON 大小和字段，固定写入目录；favicon 获取有域名白名单、逐跳检查、超时和体积限制。
- Markdown 没有启用原始 HTML；JSON-LD 转义 `<`；显式新窗口外链包含 `noopener noreferrer`。
- 对本地可达 65 个 Git 提交的跟踪文本做常见凭据模式检查，未确认泄露；模式扫描不能证明绝无秘密。

本机安装快照包含 453 个唯一 package@version。使用 GitHub 官方 `affects`（匹配任一指定包/版本）分批查询，reviewed advisories 未匹配到记录；`npm audit` 因根锁文件缺失返回 ENOLOCK，不能当作审计通过。当前 Next 16.3.4 高于官方 2026-08-25 公告的 16.3.3 修复门槛。**本次未确认严重安全漏洞，但正式构建完整依赖树、未公开漏洞和恶意包风险不在此结论保证范围内。** [GitHub Advisory API](https://docs.github.com/en/rest/security-advisories/global-advisories)、[Next 八月安全公告](https://nextjs.org/blog/august-2026-security-release)

### 7.4 安全加固不要无意破坏静态架构

正式首页有 HSTS，未观察到 CSP、X-Content-Type-Options、Referrer-Policy、Permissions-Policy 或 X-Frame-Options 响应头。缺少这些响应头属于加固空间，不等于存在可利用漏洞。

建议根据实际资源和嵌入需求逐步制定响应头策略并验证，再考虑 CSP。不要直接复制一个要求每请求 nonce 的模板：Next 官方指出 nonce 会要求动态渲染，影响静态生成和缓存。安全策略需要与站点架构一起权衡，而不是为了一个检查分数引入每请求渲染。[Next CSP 说明](https://nextjs.org/docs/app/guides/content-security-policy#static-vs-dynamic-rendering-with-csp)

### 7.5 没有测量，就难以证明优化有效

当前源码和本次页面脚本中未发现应用级访问分析、Web Vitals 或错误采集接入；这不能证明 Vercel 平台没有日志或告警配置，因为相关私有设置未核实。

最小观测建议：页面路径、关键性能、运行错误、工具外跳、Lab 导出、联系入口和商店外跳。先回答“用户是否完成了目标”，不需要同时装多套分析 SDK。不要默认采集用户搜索原文或清单内容，尤其工具可能用于工作检索；只记录必要的聚合事件，并按实际处理方式提供隐私说明。

低流量时先看明确完成事件和真实反馈，避免对极小样本的转化率下结论。主站商店外跳不等于成交；未打通独立商店数据时不能声称测到了订单转化。

## 8. 建议实施顺序

下面是实施优先级，不是安全漏洞严重度评级。工作量为粗估：小＝半天以内；中＝约 1～2 个开发日；内容补齐取决于作者真实材料，不承诺机械工期。

| 顺序 | 工作项 | 原因 | 验收方式 | 工作量 |
|---|---|---|---|---|
| 1 | 阅读时长与真实内容一致；明确联系入口 | 直接影响信任，修改成本低 | 短文不再显示虚高时长；联系动作可实际执行 | 小；联系方式需用户确认 |
| 2 | 锁文件与自动发布门槛 | 防止下一次更新破坏已有成果 | 干净检出可冻结安装；错误内容/失败测试阻止发布 | 中 |
| 3 | 主案例与一篇框架文章补证据 | 品牌与 SEO/GEO 的核心资产 | 外部读者可独立理解问题、角色、证据和限制 | 作者材料决定 |
| 4 | 手机工具搜索前置；筛选 URL 持久化 | 让收藏页真正适合日常回访 | 搜索首屏可达；刷新、分享、前进后退保留正确结果 | 中 |
| 5 | 手机菜单焦点离开处理；动效暂停与按需媒体 | 补任务可用性和无效请求 | Tab 不进入被遮挡内容；减弱动效加载不请求 MP4 | 小～中 |
| 6 | 统一内容校验与关联字段 | 让未来扩张不靠记忆和人工兜底 | 非法日期/缺封面/坏关联在检查阶段失败 | 中 |
| 7 | 最小性能、错误和任务事件观测 | 让后续优先级来自真实使用 | 能区分设备、路径、失败和关键动作；不采集不必要正文 | 中，取决于方案 |
| 8 | 搜索文本预计算、公开数据精简 | 消除重复计算，为扩张留余量 | 结果完全一致；浏览器输入测试和 payload 不退步 | 小 |
| 9 | 样式覆盖收敛、分享信息统一、文档更新 | 降低维护成本，提高分发一致性 | 视觉回归通过；分享页信息对应当前内容 | 中，可随内容迭代 |
| 10 | 部署项目清点、响应头加固、地区测试 | 治理明确、排除外部链路限制 | 项目用途/回滚清楚；策略不破坏功能；取得目标地区实测 | 需平台权限/地域条件 |

不建议同时启动所有模块。第一轮只做“发布质量 + 关键体验”，并行补一个主案例；完成后再依据数据决定扩张哪一层。

## 9. 如何验收一个更好的系统

### 性能与可用性

- 持续看真实用户移动/桌面 P75 LCP、INP、CLS；流量不足时明确标为样本不足。
- 固定环境对首页、工具、Lab 至少重复 3 次，用中位数建立后续实验室基线；当前四次单测只是审查快照。
- 320 / 390 / 768 / 1024 / 1440px 无非预期横向滚动，长标题/长工具名/空结果不破坏布局。
- 390px 手机宽度下搜索进入首屏；键盘、横屏和缩放仍可完成主要任务。
- 保留默认品牌动画；减弱动效模式不播放也不下载视频；暂停操作可键盘访问。

### 内容与任务

- 主案例有真实材料与阶段说明；“钢印 OCR 研发”等口径一致，不出现真名。
- 每个主要详情页有一个真正相关的下一步，而不是无差别跳转商店。
- 工具可以仅凭网址和分类轻松收藏；精选的判断不由导入流程伪造。
- 搜索链接可以分享和恢复；Lab 在页面已加载后断网仍可操作、本机保存并导出，不暗示具备离线首次打开能力。
- 联系入口能够对应实际沟通方式。

### 工程与维护

- 同一提交的依赖版本可复现，正式发布经过自动门槛。
- 维护入口继续在生产环境关闭，开发服务不暴露到不必要网络。
- 内容、封面、关联和实验入口在发布前验证，文档描述与当前版本一致。
- 一次普通收藏或文章更新无需同时修改多份平行索引；新 Lab 增加一个明确登记和独立交互实现即可。
- 未出现可测量需求前，不增加数据库、缓存服务、账户系统或微服务。

## 10. 证据材料与后续待确认

审查时生成的 Lighthouse JSON、浏览器记录和截图位于临时目录，未纳入版本库。报告保留了测量环境、指标与结论边界；如需复核，应在当前版本重新运行测试，而不是依赖已过期的本机路径。

后续实施前只需要补齐几个实际决定：主要访客地域、希望公开的联系方式、主案例允许展示的真实证据，以及四个 Vercel 项目的用途。其余大部分基础改进已经可以从本报告直接拆成小任务，不需要重新规划整站。

**最终建议：让它成为内容可信、任务顺畅、变更可靠的个人品牌系统。保留现有轻量架构，把复杂度留给真正出现的问题。**
